# Simple Grant AI reliability plan

## Incident and immediate release

On 20 November 2026, the production onboarding request `aaf9605a-3af1-4487-82e7-cd2467da21bd` failed in `profile_extract`. Gemini 3.8 Flash returned `MAX_TOKENS` after reporting 11,010 output tokens and 1,263 thinking tokens. Netlify logged `MODEL_OUTPUT_LIMIT` with a configured 12,288-token generation cap. The canonical site served deploy `f359157`, which was built from the onboarding pull request. Timeout, uploaded bytes and input context have separate limits. [Netlify deploy](https://app.netlify.com/projects/simplegrants/deploys/6afba43e8212162085ae61a1)

In the sampled Netlify logs, five output-limit entries spanned profile extraction, verification and draft preflight. Seven timeout entries spanned those stages and grant discovery. These counts describe observed failures. Add per-stage attempt and completion counts to measure rates.

The patch shortens the requested profile output, removes unused response fields, gives extraction and verification a 16,384-token ceiling and returns `SG_AI_OUTPUT_LIMIT` for further truncation. Run a short real-provider smoke test with fictional evidence in a separate environment. Verify the published commit when releasing from the onboarding line, then use tested production-branch builds for subsequent releases. Compare `profile_extract` success and output-limit rates against the baseline. The earlier Netlify handler crash in the runtime verification notes is a separate failure mode. ## Phase 1 · Make every failure actionable

In the first week, give each AI operation a reference at the API boundary and propagate it through enqueue, worker, provider call, status and result. Add typed failure categories for invalid source, source too large, input context exceeded, output incomplete, schema mismatch, provider refusal, app quota, provider rate limit, timeout, worker start and persistence. Keep one mapping from error category to the user’s recovery action. If a status poll drops, let the browser reconnect to the same job. If an upstream endpoint returns HTML or malformed JSON, preserve a distinct transport failure and correlate it with the Netlify request ID when available.

Log workflow, stage, deploy revision, app reference, provider request ID when available, requested and resolved model, attempt, queue delay, elapsed time by stage, HTTP status, finish reason, input/output/thinking tokens, output cap, and file counts and size bands. Keep logs free of filenames, document text, prompts, generated content and session tokens. Review failures by workflow, provider and model version. Separate app allowance, provider billable attempts and completed workflows in the metrics.

Keep the packaged runtime checks in CI. Extend them with controlled output truncation, an oversized input, refusal and schema failures, provider throttling, lost polling responses, concurrent retry, worker restart, and a failure after generating but before saving. Add post-deploy smoke tests with synthetic evidence and alert on sustained failures. Keep the deploy’s working configuration available for rollback. ## Phase 2 · Give each operation a budget and a durable job

Build a shared execution layer with per-stage policies for source bytes, input context, generation, thinking where supported, elapsed time, attempts and cost. Pin evaluated model versions where available and record the resolved model. Estimate text and multimodal input separately, leaving room for instructions, schemas, grounded tool results and the expected output. Check storage size and document structure before charging quota. Separate malformed files from files that need chunking.

Convert each supported document once per version, using its content hash and extractor version inside the organisation’s access boundary. Index bounded passages by document, page, sheet or row. Send only the passages relevant to each task, with source pointers and enough surrounding text to verify the quote. For long evidence, extract bounded facts by chunk, merge them in code and preserve contradictions for review. Apply the same evidence rules to pasted text. Keep the original in the private library and tell the user when some evidence needs separate review.

Use strict provider schemas and validate the result again in the app. Keep tasks that copy known fields or check identifiers deterministic. For truncated output, spend at most one policy-approved recovery attempt with a smaller scope or a different output budget justified by tests. For temporary network errors, throttling and provider overload, use bounded backoff with jitter under the job deadline and honour provider retry hints. Use typed terminal failures for invalid input, permission and permanent configuration errors. A recoverable failure should expose the failed stage and preserve validated earlier work.

Replace the current one-time Storage launch and claim with a durable job record, persistent checkpoints, and a queue or transactional outbox. Use the existing Supabase project’s Simple Grant namespace. Consider Supabase Queues after checking extension availability and shared-project boundaries. Store references to private evidence and a request fingerprint in the queue. Enqueue once per idempotency key, lease work with an expiry, and recover abandoned leases. Recheck permissions and source revisions at resume and write time. Guard database effects and email sends with idempotency keys. Track ambiguous provider attempts separately so redelivery is never treated as a guarantee of single billing. Retain result and retry state long enough for refresh and resume. Expire artifacts through a retention policy.

Keep short interactive calls on a measured request budget. Put longer or multi-stage work behind the shared queue. The portal should show queued, running, needs input, ready for review and retryable failure states, with an option to return later. Start with onboarding and validate the design before moving the high-value workflows below. ## Phase 3 · Roll out by workflow

| Order | Workflow                                                | Apply the shared controls                                                                                                                                                                                                                                             |
| ----- | ------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1     | Organisation onboarding                                 | Bound extraction and evidence quotes, checkpoint verification, retain the uploaded originals, and require human approval. Evaluate with bilingual sources, scanned documents, conflicting legal names and missing fields.                                             |
| 2     | Application research, preflight and drafting            | Keep public source research separate from private organisation evidence. Retrieve evidence per requirement and draft in section-sized tasks. Preserve official guidelines, eligibility blockers, word limits, previous user edits and evidence links through retries. |
| 2     | Progress and acquittal reports                          | Aggregate ledger totals and date ranges in code, check data revisions before saving, and draft only the narrative from scoped evidence. Retain explicit human review.                                                                                                 |
| 3     | Grant discovery, guideline import and scheduled digests | Separate search, source validation, extraction and delivery. Verify official sources, dates and citations, and deduplicate writes and sends across retries. Give the digest the same durable worker as the portal, with a per-organisation and per-period send key.   |
| 4     | Portal questions and inbound email                      | Keep short portal questions on a small deadline and context budget. Let the webhook record the event and acknowledge it promptly. Move optional AI classification to the queue and preserve the existing public-information limits for outbound replies.              |

## Initial service objectives

Use these as starting targets. Measure the first two weeks, then adjust thresholds and staged rollout sizes using the baseline.

| Measure                                                                                      | Initial target                                                                                                                                                                                                                                             |
| -------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Valid interactive workflows reaching review or a usable answer, including automatic recovery | At least 99% over a rolling 30 days, tracked per workflow. Count provider, infrastructure and validation failures. Report user cancellations and invalid requests separately.                                                                              |
| Job acceptance and start                                                                     | 95% acknowledged within 2 seconds. 95% start within 10 seconds.                                                                                                                                                                                            |
| End-to-end profile and document jobs                                                         | 95% of profiles ready for review within 90 seconds. 95% of longer drafts, reports and grant searches ready within 3 minutes. Track queue wait and provider time separately.                                                                                |
| Error traceability                                                                           | At least 99% of server-reported failures have a searchable reference.                                                                                                                                                                                      |
| Quality and consistency                                                                      | Zero duplicate database effects or digest sends in crash-and-retry tests. Zero incorrectly approved profiles or applications in the release fixtures. Track first-pass schema validity, evidence accuracy and the share recovered after output truncation. |

Alert immediately on a synthetic workflow failing twice in succession, and on a workflow falling below 95% completion across at least 20 eligible runs in one hour. Track the oldest queued job and repeated permanent failure categories even at low volumes. Review alert volume and targets after the baseline period.

## OpenAI decision

Keep Gemini as the primary provider while releasing and measuring the onboarding fix. Pilot the OpenAI Responses API behind the shared adapter for structured profile extraction or draft sections. OpenAI Structured Outputs can enforce a response schema on supported models. Its output cap still includes reasoning tokens, and incomplete responses and refusals need explicit handling. Gemini grounding carries search metadata that the app uses for citation handling. Evaluate search and source validation separately before routing discovery to another provider. [OpenAI Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs?api-mode=responses) · [OpenAI Responses API](https://developers.openai.com/api/reference/resources/responses/methods/create)

Run both providers against the same versioned, consented or fictional evidence set. Include bilingual and scanned sources, long guidelines, sparse inputs, contradictory facts, grant citations and word limits. Compare field-level evidence accuracy, unsupported facts, first-pass and final completion, truncation and refusal rates, p95 latency, and total cost per successful workflow including retries. Review document data handling and retention before sending real materials to another provider. A candidate must preserve evidence quality and meet the service targets. Use a per-workflow feature flag, a limited canary and the previous route for rollback. Choose one provider per stage by default and use an alternate provider only for measured, classified failures covered by the workflow’s policy.
