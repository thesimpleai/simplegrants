# Supabase data model

Simple Grant uses its own `simple_grant` schema and private `simple-grant-documents` bucket inside a shared Supabase project. It does not reuse `public.documents`, move another application's tables, modify existing functions, change Auth configuration, or update another application's migration history. All table and function names below belong to `simple_grant` unless otherwise stated.

## Shared-project installation

1. Save the single JSON result from the read-only `supabase/verify-shared-project.sql` before installing. This captures object names/status and an unrelated catalog/config fingerprint, not application records or credentials.
2. Run `supabase/install-simple-grant.sql` once in the selected project's SQL Editor. The generated script wraps all six canonical baselines in **one transaction**. It deliberately fails if the `simple_grant` schema already exists; investigate rather than dropping it or forcing a rerun. If its dedicated bucket already exists but is public or has incompatible MIME/size settings, the whole installation rolls back without reconfiguring that bucket.
3. Append `simple_grant` to the project's existing API exposed schemas list, preserving every existing entry. The application explicitly targets that schema and the dedicated bucket; it has no `public` fallback.
4. Run the read-only verification query again. Compare `unrelated_metadata_fingerprint` and `unrelated_object_count` with the saved pre-install result. A match is evidence of unchanged catalog/config metadata only; it does not verify application records, hosted API behavior, or the correctness of old policies. Without a pre-install result, do not claim historical equality.

Use `node supabase/build-installer.mjs` to regenerate the installer and `node supabase/build-installer.mjs --check` (or `npm run db:check`) to check it matches the six canonical files. Do not run `supabase db push`, `db reset`, or migration repair against the shared project's existing migration history. These baselines are not an upgrade or automatic data migration from any legacy `public` Simple Grant installation.

### Upgrade an existing installation

If Simple Grant already has 001–005, apply only `supabase/migrations/202611100006_document_formats.sql` in SQL Editor. Migration 006 extends the MIME allowlist of the private `simple-grant-documents` bucket and preserves its existing additional MIME entries; it does not change organisation/document rows, RLS policies, privacy, other buckets or shared Auth settings. It requires the dedicated bucket to exist, remain private, retain the 10 MiB size limit and have a finite MIME allowlist. A missing or incompatible bucket must be investigated rather than replaced or made public. Repeating the MIME upgrade is safe when it is already applied and does not rewrite an unchanged allowlist.

If the installation stops at 004, apply 005 then 006 without rerunning installed baselines. Migration 005 adds the auth request table and service RPCs described below. Fresh installations use the combined six-baseline installer. There are still 13 Simple Grant tables; 006 creates no new table. Never remove the schema or alter unrelated migration history to apply these upgrades.

Preserve the shared project's Auth Site URL, SMTP/signup settings, templates and redirects. The app-owned login callback does not require another global Auth redirect. A service-role credential can access other applications' data by design; keep it server-side. Namespace and RLS isolation do not isolate the trusted SQL administrator or a compromised service-role key.

## Organisation ownership

A login can belong to any number of organisations. `organization_members` is the source of truth for tenant access. Authenticated clients call `create_organization(p_name, p_frequency)` to atomically create an organisation and their `owner` membership. No client can insert, update, or remove membership records. Team invitation and role management are future server-mediated workflows; do not grant a client the service role key to work around this.

| Role   | View organisation and evidence | Change profile, applications and evidence | Delete organisation |
| ------ | ------------------------------ | ----------------------------------------- | ------------------- |
| owner  | Yes                            | Yes                                       | Yes                 |
| admin  | Yes                            | Yes                                       | No                  |
| member | Yes                            | Yes                                       | No                  |
| viewer | Yes                            | No                                        | No                  |

The organisation profile's `verification_status` records human approval (`draft`, `review`, `approved`), not verification by ACNC or an auditor. `documents.verified` is a user review flag, not an audit opinion. Store no bank details in the profile. Uploaded evidence can contain personal or financial information and remains private.

## Main records

- `organizations`: organisation identity, flexible profile JSON, Australian state, focus areas, notification frequency and random inbound email alias. The alias is not an authentication mechanism; inbound processing must still verify provider signatures and the sender's membership.
- `documents`: private evidence metadata. Object paths start with the organisation UUID. The canonical MIME allowlist has 13 entries covering PDF, PNG, JPEG, WebP, plain text, CSV, TSV, Markdown, JSON, HTML, XML, DOCX and XLSX, with a 10 MiB per-file bucket limit. Uploads accept at most ten files per batch; an AI request selects at most eight documents and 15 MiB total, with additional extraction/archive limits. Each text extraction is capped at 200,000 characters, with 400,000 converted-text characters across the selected documents per AI request; Office archives allow at most 512 entries and 20 MiB expanded bytes. DOCX/XLSX are converted to text before Gemini use. See the full processing limits in `DEPLOYMENT.md`. The shared format policy normalises known browser MIME aliases without making unsupported extensions valid. Files are not public. During a fresh baseline installation, an incompatible pre-existing `simple-grant-documents` bucket causes rollback rather than silent reuse. The reviewed 006 upgrade above is the supported extension of this dedicated bucket's MIME list. Resolve that dedicated bucket naming conflict before retrying; never reuse or reconfigure another application's bucket.
- `opportunities`: source URL, provenance, known opening and closing times, guidelines, eligibility requirements and estimated match score. Unknown values remain null. Source provenance does not prove eligibility.
- `applications`: original opportunity, project information, AI-assisted draft, review/submission status and the external submission reference. A status change is not an automated funder submission.
- `funded_projects`: accepted funding, original proposal, budget JSON, milestones, reporting date and persisted `report_draft` JSON object. Draft reports remain subject to human review and external submission.
- `expenses`: non-negative expenditure and optional evidence document, attached to a funded project.
- `inbox_messages`: inbound communications and attachment metadata, requiring review before affecting a budget or grant record.
- `activity_log`: server-authored event history, visible to organisation members. Clients cannot forge log entries.

Every dependent record carries `org_id`. Composite foreign keys enforce that an application's opportunity, project's application, expense's project/document, and inbox message's project belong to that same organisation. Triggers prevent changing an existing record's organisation. Membership helper functions are `SECURITY DEFINER` with fully qualified references and empty `search_path` to avoid recursive RLS and object-shadowing attacks.

Private Storage policies separately enforce membership for the first path component. Four Simple Grant permissive policies allow appropriate member operations. Four additional `AS RESTRICTIVE ... TO PUBLIC` policies fence only `simple-grant-documents`, because an existing project's permissive policies combine with OR and might otherwise expose it. Their conditions evaluate true for every other bucket, preserving existing access rules. They apply to every non-BYPASSRLS role, including anonymous and custom application roles. The service role intentionally bypasses RLS.

Only the safe membership boolean and path-parsing helpers are publicly executable; unauthenticated membership checks return false. They need schema USAGE/function EXECUTE even when PostgreSQL initializes a storage expression for another bucket. Public roles receive no table rights, schema CREATE, organisation-creation RPC, or service-job RPC access. Inherited default ACL grants are removed on newly created Simple Grant objects only, then the intended ACLs are granted. Existing global defaults, public tables and functions remain unchanged.

Existing restrictive Storage policies continue to apply. The supplied shared-project definitions restrict authenticated PDF SELECT/INSERT to `pdfs` and exclude `finance-evidence` for anon/authenticated; those exact predicates are compatible with `simple-grant-documents` and pass the local regression without changing the old rules. Authenticated PDF UPDATE/DELETE remain denied, and service-role finance bypass remains. Names alone cannot establish compatibility for other or future policies. Test hosted storage after installation; do not remove or relax another application's policies to make uploads pass. Signed URLs, if created, are temporary bearer access and should not be emailed or logged.

## Service-only processing

`notification_runs` has a unique `(org_id, period_key)`. `claim_notification_run(p_org_id, p_period_key)` atomically claims a new, failed, or stale processing run. Columns are `id`, `org_id`, `period_key`, `status` (`processing`, `sent`, `failed`), `last_error`, `provider_message_id`, `started_at`, and `completed_at`.

`webhook_events` uses the provider `event_id` as its primary key. `claim_webhook_event(p_event_id, p_event_type)` atomically claims new, failed, or stale processing deliveries. Columns are `event_id`, `event_type`, `status` (`processing`, `processed`, `rejected`, `failed`), optional `org_id`, `received_at`, `processed_at`, and `last_error`.

Both claim functions and both tables are service-role only. A processing lease is reclaimable after 15 minutes; completed or rejected events cannot be reclaimed. Providers and workers must also use deterministic email idempotency keys, and attachment storage should use deterministic object paths, because database claiming cannot alone guarantee exactly-once external delivery. Never mark a notification `sent` until the email provider accepts it. Do not put sensitive request bodies, API keys or document contents into error metadata.

## Deployment verification

The six-baseline installer and upgrades are exercised in four disposable PostgreSQL 17 scenarios with minimal Supabase `auth`/`storage` stubs: a fresh adversarial shared-app fixture, a fresh exact-existing-policy fixture, an 001–004 installation upgraded through 005 and 006, and an existing 001–005 installation receiving 006 alone. That fixture includes an existing `public.documents` row, colliding public function names, private/public legacy buckets, broad legacy permissive storage access, an unrelated restrictive finance-bucket policy, pre-existing CLI history, and global default ACL grants to anonymous/authenticated/custom roles.

The regression compares unrelated metadata fingerprints before and after installation; checks the legacy document/history sentinel records and old storage behavior; and exercises Simple Grant organisation ownership, tenant/foreign-key isolation, role restrictions, storage read/write/update/delete boundaries for anonymous/authenticated/custom roles, inherited-ACL cleanup, service-only job claiming and shared AI quotas. The fresh scenarios also verify successful owner storage SELECT/INSERT/UPDATE/DELETE and cross-organisation, viewer-write and anonymous denials. The exact-definition scenario confirms authenticated legacy PDF SELECT/INSERT and denied UPDATE/DELETE both before and after installation, plus unchanged finance denials and service-role bypass. A public dedicated-bucket conflict must roll the entire installer back. Reapplying the baseline must fail safely rather than silently reuse a namespace.

The 006 checks also preserve existing document/object records and additional bucket MIME entries, exercise metadata writes for the eight new formats, and prove that a repeated upgrade leaves the bucket row unchanged. Missing/public/wrong-size/unrestricted-MIME bucket guards fail without mutation. These are SQL catalog/data checks, not actual file-byte uploads through Storage.

This validates PostgreSQL logic, not the hosted Supabase Auth, Storage API, API-schema exposure or live email/Gemini integrations. No hosted database has been modified or verified by these local tests. Run `bash supabase/tests/run-local.sh` for the disposable test. Never run fixture/bootstrap/security-test writes against a live shared project. Hosted readiness still requires its separate sign-in, storage and application checks after configuration.

## Durable AI request budget

`ai_usage` is a service-only table keyed by `(user_id, usage_date)`. Authenticated callers execute `claim_ai_request(p_org_id, p_action)` immediately before a billable AI operation. The function requires membership, and requires owner/admin/member editing privileges for every action except `ask`. Only `profile`, `discover`, `import-grant`, `draft`, `ask`, and `report` are accepted. An atomic conditional upsert enforces at most 60 user-initiated requests per user per UTC calendar day across all their organisations. Calls above the limit return `false`; unauthorised or invalid actions raise an error. Clients cannot read, alter, or reset the counter. Failed downstream operations still consume a claimed request; each of the three separately authenticated profile stages claims one request, so a completed extraction/check/correction sequence consumes three. The interface retry restarts all three stages; every successfully claimed stage in that retry consumes another request. This is an application guardrail, not a provider billing limit or global organisation quota; scheduled service jobs require their separate scheduler bounds.

Profile preparation keeps `action=profile` and sends `profileStage=extract`, `verify` and `correct` as separate authenticated requests. The server recomputes a source fingerprint from the organisation, pasted text, selected document IDs/bytes and ordered extracted content. Later stages reject changed originals with HTTP 409. Intermediate drafts/checks are transient client state; only the corrected result is presented for explicit human approval. No extra table or background job is introduced for the staged preparation.

`claim_email_ai_request(p_org_id, p_user_id)` is a service-role-only counterpart for the optional public-only inbound email reply worker. It verifies the explicitly supplied user's organisation membership, then atomically consumes the same user/UTC-day counter. It cannot be executed by authenticated or anonymous clients. Portal and email requests together are capped at 60 per user per day. The webhook must verify its provider signature and sender membership before calling this helper; the helper does not establish email authenticity or authorise access to private documents.

## App-specific sign-in email support (005)

`auth_email_requests` is service-only and has four fields: random request `id`, 64-character lowercase HMAC-SHA256 `email_hash`, matching-format `ip_hash`, and `claimed_at`. It stores no raw email or IP address. The server must derive domain-separated fingerprints with an independent secret containing at least 32 cryptographically random bytes; this secret must never have a `VITE_` prefix.

The service-only `claim_auth_email(p_email_hash,p_ip_hash)` returns a claim UUID or null. Claims consume a 60-second email cooldown, at most 5 attempts per rolling hour per email and 20 per rolling hour per IP. These limits apply before account lookup/link generation, including unknown-account attempts. The function takes sorted transaction advisory locks across the email/IP keys and samples time after acquiring them. It supports the normal READ COMMITTED API isolation level and fails closed under custom snapshot isolation. A hash collision in the advisory lock key can add contention, not bypass the keyed limits. Up to 200 events older than 24 hours are removed per successful claim; this is bounded opportunistic cleanup, not a guaranteed background TTL.

The service-only stable `auth_email_user_exists(p_email)` returns whether a case-insensitive exact address exists in shared `auth.users`. It does not expose users through a browser RPC, require copying Auth data into app tables, or change signup/SMTP/Site URL settings. Anonymous, authenticated and custom app roles have no access to either auth-email RPC or the request table; inherited default ACL grants are removed only from these newly created Simple Grant objects. Login responses and signup eligibility remain server decisions, with generic acknowledgements that do not disclose account or delivery status.

The local suite includes direct cooldown/hourly-limit/expiry/prune checks and genuinely concurrent RPC transactions: twelve requests for one email across distinct IPs allow one claim; twenty-five distinct emails from one IP allow twenty claims. A separate fresh fixture installs 001–004, preserves a synthetic existing organisation, applies 005 alone and then runs the same security/rate tests. This does not establish that hosted email delivery or login verification works; those require separate deployed checks.
